# 운영 절차

## 배포 전

1. `git status`로 의도하지 않은 파일이 없는지 확인합니다.
2. `pnpm lint`, `pnpm build`, `pnpm audit --prod`를 모두 통과시킵니다.
3. 신규 SQL이 있으면 Supabase 백업 상태와 복구 가능 시점을 확인합니다.
4. 마이그레이션의 사전 점검 쿼리를 먼저 실행합니다.

## DB 마이그레이션

운영 DB에서는 `supabase/migrations`의 신규 번호 파일만 실행합니다. `supabase/manual` 파일은 자동 또는 일괄 실행하지 않습니다.

`0025_security_hardening.sql` 적용 전에는 다음 쿼리가 0행인지 확인합니다.

```sql
select member_id, count(*)
from profiles
where member_id is not null
group by member_id
having count(*) > 1;
```

마이그레이션은 트랜잭션으로 실행되며, 오류가 발생하면 앱을 먼저 배포하지 않습니다.

## 배포 순서

DB 함수와 앱 코드가 함께 변경된 경우:

1. 운영 DB 백업 확인
2. 신규 마이그레이션 실행
3. 마이그레이션 사후 점검
4. 앱 배포
5. 로그인·참석·운영진 화면 스모크 테스트

## 필수 스모크 테스트

- 비로그인 사용자가 `/`와 `/admin/team`에서 로그인 화면으로 이동
- 일반 회원이 운영진 페이지에 접근할 수 없음
- 본인 참석/불참 변경 가능
- 자체전 레드/블루 배정은 운영진만 변경 가능
- 가입 신청 승인·거절 가능
- 결과 저장 시 용병명이 `용병`으로 익명화
- 결과 입력 후 참석자끼리만 MOM 투표 가능
- 크론 URL을 인증 없이 호출하면 `401`

## 백업과 복구

- Supabase 자동 백업 보존 기간을 월 1회 확인합니다.
- 중요한 마이그레이션 전 수동 백업 또는 PITR 복구 지점을 확보합니다.
- 분기 1회 별도 테스트 프로젝트에서 복구를 검증합니다.
- Vercel 롤백은 앱 코드만 복구하며 DB 스키마는 자동으로 되돌리지 않는다는 점에 유의합니다.
